# 任务经验闭环

把一次多步骤任务同时做成“完成当前目标”和“留下可复用经验”两条闭环。目标是让后续类似任务更快找到正确路径，也更早知道哪些坑不能踩。

## 适用边界

- 适用于跨越多个文件或步骤的实现、调试、故障定位、构建、测试、迁移和发布任务。
- 跳过拼写修正、一次性查询、简单单步编辑等没有可复用决策的任务。
- 用户明确要求不要写文件、只做分析或保持工作区不变时，不创建或修改经验文件；仍可在最终答复中简要总结候选经验。
- 只维护当前项目。不要自动写 `AGENTS.md`、全局 skill 或其他项目的记忆，也不要把一次任务的经验当成跨项目通用事实。

## 任务开始：先检索

1. 根据用户目标、代码入口、错误文本和涉及子系统提炼 2–6 个具体检索词，例如技术栈、错误码、命令、组件名和根因短语。
2. 若项目根目录存在 `LESSONS.md`，先读所有 `Promoted` 强制检查，再只读与当前任务最相关的已核实条目。没有 `LESSONS.md` 时继续工作，不要在尚无经验可写时创建空文件。
3. 若 `.agents/experience/sessions/` 存在，可检索其中未合并的相关候选经验；优先最近记录，最多读取 3 份。
4. 把旧经验当作待验证提示。结合当前源码、依赖版本和运行环境确认仍然适用；已失效的经验应更新或标记 `Superseded`，不要机械照搬。
5. 记住本次实际复用了哪些经验，但不要在过程答复中逐条复述，除非它影响当前决策。

## 任务进行：只记高价值事件

出现以下任一情况时，才建立或追加过程日志：

- 同一问题经过多个方案才定位根因，或一次修复后被用户指正/返工。
- 发现不明显的环境、工具链、依赖、权限、缓存或测试约束。
- 找到并验证了可复用的成功路径。
- 用户做出了会影响后续实现的产品、安全或架构决定。
- 某个检查确实没有执行，且这个缺口会影响“已完成”的结论。

不要记录普通命令流水账、无根因的报错原文、通用最佳实践、凭据或原始敏感配置。

首次出现高价值事件时，先确认项目 `.gitignore` 忽略 `.agents/experience/`；尚未忽略时补上该条，除非用户限制文件修改。然后创建 `.agents/experience/sessions/<YYYYMMDDTHHmmss>-<slug>.md`。使用当前本地日期时间和简短的 kebab-case 任务名；如同名文件已存在，追加序号。先读 [经验文件格式](references/ledger-format.md)，再按其中模板记录现象、尝试、根因、解决过程、证据和候选规则。

边发生边记事实，不要事后补写不存在的尝试。长期运行、上下文压缩前或任务中断前，应把尚未落盘的重要候选经验写入当前日志。

## 任务收尾：合并、去重、升级

在任务完成、主要阶段完成或即将结束会话时，读 [经验文件格式](references/ledger-format.md)，执行一次合并：

1. 把过程日志拆成 `Verified`、`Open` 和 `Not run`。任务成功不等于修复已验证；没有证据的根因或解法保持 `Open`。
2. 按根因和预防方法检索 `LESSONS.md`，不要只按措辞匹配。相同根因合并到现有条目；不同根因才新增。
3. 同一任务同一天多次触发只记为一个日期。只有跨不同日期再次发生，才增加 `Seen` 次数。
4. 首次经验写入项目根目录 `LESSONS.md`；文件不存在时从参考模板创建。记录一句话规则、适用范围、触发条件、根因、解法、证据、`Done right` 和出现日期。
5. 一条经验在 3 个不同日期复现且状态为 `Verified` 时，标记为 `Promoted`，并在文件顶部“强制检查”区增加一条可执行的检查。未核实经验不得升级。
6. 更新过程日志状态为 `Consolidated` 并写明合并结果。不要删除历史证据；过时条目标记 `Superseded` 并说明日期和原因。
7. 多个任务可能同时更新 `LESSONS.md`。修改前重新读取目标条目，保留已有日期和其他人的内容，再做最小合并。

## 完成标准

- 相关旧经验在动手前被检索并重新验证。
- 关键失败、根因和已验证解法有可追溯证据。
- 重复问题按不同日期累计，而不是按同一天的多次尝试刷次数。
- 三次复现的已核实经验已成为后续任务必读的强制检查。
- 未验证、未运行和已失效的信息没有被写成确定结论。
- 最终只在有实际变化时说明复用了哪些经验、更新或升级了哪些规则；没有值得沉淀的内容时保持安静。

## 隐私与准确性

- 不写入令牌、密码、Cookie、个人信息、签名 URL、完整环境变量值或其他秘密；用 `[redacted]` 保留判断所需的结构。
- 区分 `Observed`、`Verified`、`Open`、`Not run`，不要把推测写成根因，也不要把“测试通过”扩大成“真实使用已验证”。
- 用户明确确认的产品、安全或架构决定是后续约束。新证据与其冲突时先提出冲突，不要自行反转。
