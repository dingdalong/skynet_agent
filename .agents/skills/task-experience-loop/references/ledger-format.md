# 经验文件格式与维护规则

在首次创建过程日志、创建 `LESSONS.md` 或合并经验时读取本文件。`SKILL.md` 决定何时记录；本文件定义如何写得可检索、可验证、可维护。

## 存储分层

| 层级     | 路径                              | 是否提交                   | 用途                                             |
| -------- | --------------------------------- | -------------------------- | ------------------------------------------------ |
| 过程日志 | `.agents/experience/sessions/*.md` | 否，应由 `.gitignore` 忽略 | 保存当前任务的原始事实、失败尝试和待合并候选经验 |
| 长期经验 | `LESSONS.md`                      | 是                         | 保存去重后的经验、成功路径、重复次数和强制检查   |

`.agents/experience/` 只服务当前工作区。不要把它同步到全局目录，也不要依赖其他项目中的经验。第一次创建该目录时，确认项目 `.gitignore` 已包含 `.agents/experience/`；缺失时补上。`LESSONS.md` 只在第一次有值得长期保留的经验时创建，避免空文件。

## 过程日志模板

文件名使用 `<YYYYMMDDTHHmmss>-<slug>.md`。一个任务一份文件；多个 agent 并行时分别使用自己的时间戳，避免覆盖。

```md
# 任务经验日志

- 状态：In progress
- 任务：<用户目标的一句话摘要>
- 日期：<YYYY-MM-DD>
- 范围：<涉及目录、服务或功能>
- 标签：<technology>, <subsystem>, <symptom>
- 复用的旧经验：<LESSONS.md 条目 ID；没有则写 None>

## 事件

### E1: <一句话现象>

- 触发条件：<输入、环境、命令、版本或操作路径>
- 原始证据：<最小必要错误、测试结果、文件或命令；敏感值标为 [redacted]>
- 尝试：<按时间列出真正执行过的方案及结果>
- 根因：<已验证的根因；未确认时写 Open>
- 解法：<实际改动或操作>
- 验证：Verified | Unverified | Not run
- 验证证据：<回退测试、复现前后结果、真实环境结果；未执行时写原因>
- 候选规则：<一句可执行、可迁移到同类问题的话>
- Done right：<可选：可复用的成功策略>
```

在任务结束或主要阶段结束时，把状态改为 `Consolidated`，并增加：

```md
- 合并结果：<更新了哪个 LESSONS ID、升级了哪条规则，或 Why no durable lesson>
```

## 长期经验模板

`LESSONS.md` 始终使用下面结构。新经验追加到“经验明细”，只有已升级的检查才进入顶部区域。

```md
# Project Lessons

后续 agent 在相关多步骤任务开始前，先读本文件的强制检查，再检索与当前问题匹配的经验明细。

## 强制检查

<!-- 仅有三次不同日期复现且 Verified 的经验进入这里。 -->

- **LC-001** <可执行检查>。证据见 L-001。

## 经验明细

### L-001: <一句话规则>

- 类型：Pitfall | Success
- 状态：Open | Verified | Promoted | Superseded
- 范围：<技术栈>, <子系统>, <触发场景>
- 触发：<何时应想到这条经验>
- 根因：<已验证根因；未知时明确写 Unknown>
- 解法：<已执行并验证过的步骤>
- 证据：<测试名、复现命令、提交、文件或真实环境结果>
- Done right：<可选：应复用的成功路径>
- Seen: 1× (YYYY-MM-DD; task: <session file or commit>)
- 备注：<未运行检查、适用范围或 Superseded 原因>
```

ID 使用稳定、只增不减的 `L-NNN`；强制检查使用对应的 `LC-NNN`。不要重排已有 ID 让历史引用失效。

## 何时创建条目

值得长期保留的内容通常满足至少一项：

- 已经导致返工、误判、重复尝试或用户纠正。
- 揭示了非显然的系统边界、顺序依赖、缓存行为、版本差异或验证盲区。
- 是可复制的成功路径，能显著减少下一次同类任务的探索。
- 是用户明确做出的持久决定，后续实现不能无意反转。

以下内容通常只留在过程日志，不进入 `LESSONS.md`：

- 普通命令、常规编辑和一次就成功的标准流程。
- 没有根因、没有可复用行动项的大段日志。
- 已由代码、README 或测试直接表达的普通项目事实。
- 只在一次性环境损坏中出现、无法给出预防措施的偶发情况。

## 状态含义

- `Open`：已经观察到问题，但根因、解法或验证至少有一项未确认。
- `Verified`：在适用环境中复现了问题，修复后同一检查通过；必要时应包含回退验证。
- `Promoted`：`Verified` 且在 3 个不同日期出现，已经进入强制检查区。
- `Superseded`：已被新事实或新规则取代；保留历史，写明替代条目和日期。

`Not run` 是验证空缺，不是 `Open` 的同义词。环境不具备、权限不足或时间不够时，明确写出未运行的检查及其影响。不要把编译通过、代码审查、任务状态成功或代理自述当作真实使用验证。

## 去重与重复计数

合并前用根因关键词、组件名、错误类型和预防动作检索 `LESSONS.md`。按“同一根因导致同一类错误，并需要同一预防措施”判断是否重复，而不是只比较现象句子。

- 同一条经验在同一个本地日期的多次重试只算一次。
- 不同日期再次真实发生，才把新日期追加到 `Seen`。
- 相同日期已有记录时，补充新的任务引用，但不要增加次数。
- 根因不同、边界不同或所需预防措施不同的情况应拆成独立条目。
- 三个不同日期是升级门槛；大量同一天报错不能代替跨日复现。

升级时：

1. 确认状态为 `Verified`。
2. 把条目状态改为 `Promoted`。
3. 在顶部加入简短、命令式、可执行的 `LC-*` 检查。
4. 保留原条目、证据和全部日期，供后续审查。

## 证据规则

证据应足够让另一个 agent 判断结论是否仍成立：

- 代码问题：最小复现命令、失败断言、修复后的同一检查。
- 回归修复：先证明旧行为会失败，再证明新行为通过；测试被跳过或根本没运行时不能算回退验证。
- UI/交互问题：在用户实际使用的界面、尺寸和输入路径上复现，不能只修截图中的单一状态。
- 外部集成：记录真实配置或真实接口返回时，只保留脱敏后的结构和结论。
- 环境问题：记录操作系统、运行时版本、相关工具版本和决定性日志。

如果无法执行某项验证，在日志和长期经验中写 `Not run: <原因与影响>`。不要用省略代替未运行。

## 成功经验

`Success` 条目和 `Done right` 不是庆祝记录，而是下一次可照做的路径。写清楚为什么有效、在哪些条件下有效，以及最小验证方式。若成功路径依赖特定版本、平台或账户，把这些边界写入“范围”和“备注”。

## 并发与隐私

- 每个任务只编辑自己的 session 文件；合并 `LESSONS.md` 前重新读取目标段落。
- 不使用整文件覆盖来合并长期经验，避免丢掉并行任务刚写入的内容。
- 不记录令牌、密码、Cookie、个人信息、签名 URL、完整环境变量值或大段生产数据。
- 不为了留下经验而重复执行有副作用、会花钱或会改变外部状态的验证。
